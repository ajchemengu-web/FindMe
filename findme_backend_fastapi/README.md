# FindMe backend -- FastAPI edition (replaces the Supabase backend)

This replaces `findme_backend/` (Supabase: Postgres+PostGIS, Auth, PostgREST, Storage,
Edge Functions) with a self-hosted service this app owns end to end: FastAPI +
SQLAlchemy (async) + PostgreSQL/PostGIS, custom JWT auth, and S3/MinIO for file
storage. The old `findme_backend/` folder is left untouched next to this one for
reference (its migrations were the source of truth this rewrite was ported from) --
once this service is deployed and the mobile app is repointed at it, that folder can be
retired.

## Why this exists

The project moved off Supabase. Nothing about the product changed -- every table,
every authorization rule, every plan limit, every billing flow is the same. What
changed is who enforces it: Supabase's Row Level Security policies and Postgres
triggers did that work invisibly before; now `app/services/authz.py` and each
`app/routers/*.py` file do it explicitly, in Python, in this repo.

## Stack

- **FastAPI** + **SQLAlchemy 2.0 (async, asyncpg)** -- the API layer and ORM.
- **PostgreSQL 16 + PostGIS** -- same database engine as before, self-hosted instead of
  managed. `geography(point, 4326)` columns, GIST indexes, and `ST_DWithin` geofence
  math are unchanged.
- **Custom JWT auth** (`app/core/security.py`) -- bcrypt password hashing, short-lived
  signed access tokens, opaque rotating refresh tokens stored hashed in the database
  (so they're actually revocable, unlike a bare stateless refresh JWT would be).
- **Alembic** -- one hand-written initial migration (`alembic/versions/0001_initial.py`)
  that creates the full schema. Hand-written rather than autogenerated because no live
  Postgres was available in the sandbox this was built in -- see "Verification" below.
- **boto3 -> S3 or MinIO** -- replaces Supabase Storage's `avatars`/`intel-photos`
  buckets.
- **httpx** -- outbound calls to the Guardian API (news), Safaricom Daraja (M-Pesa),
  Expo's push API, and (optionally) Twilio.

## Running it

```
cp .env.example .env      # fill in JWT_SECRET at minimum (openssl rand -hex 32)
docker compose up --build
docker compose exec api alembic upgrade head
```

The API is then at `http://localhost:8000`, MinIO console at `http://localhost:9001`
(user `findme` / password `findme12345`).

Without Docker: point `DATABASE_URL` at any Postgres+PostGIS instance, `pip install -r
requirements.txt`, `alembic upgrade head`, `uvicorn app.main:app --reload`.

## What changed vs the Supabase version (read this before deploying)

**Row Level Security and triggers -> `app/services/authz.py`.** This is the single
biggest architectural change and the biggest risk if it's ever forgotten. Under
Supabase, even a raw SQL query or a misbehaving client could not bypass an RLS policy
-- the database refused the read/write no matter which code path reached it. Here,
authorization is Python code that every router has to remember to call. A future
router or script that queries `devices`/`consents`/`location_pings`/`geofences`
directly without going through `app/services/authz.py` will leak data that RLS would
have silently blocked. Mitigate this by keeping ALL access to those tables inside the
existing routers/services, and by writing new authorization-sensitive endpoints as
services-layer functions first, the way `authz.py` is structured now.

**Plan-limit triggers -> synchronous checks before each write.** Same risk as above,
scoped down: `check_device_create_limit`/`check_precise_scope_allowed`/
`check_watch_limit_on_approve`/`check_geofence_create_limit`/
`check_watch_topic_create_limit` in `authz.py` replace the five `BEFORE INSERT/UPDATE`
triggers from `20260702121300_billing.sql`/`20260702121600_mpesa_billing.sql`. They're
called explicitly in each router; there's no database-level backstop if a new write
path forgets to call one.

**`updated_at` triggers -> SQLAlchemy `onupdate=func.now()`.** Functionally
equivalent for any write that goes through the ORM. A raw SQL `UPDATE` issued outside
SQLAlchemy would skip it, unlike the old Postgres trigger, which fired regardless of
how the row was written.

**Supabase Auth -> `app/core/security.py` + `app/services/auth.py`.** Full custom
implementation: bcrypt hashing, short-lived JWT access tokens, opaque refresh tokens
hashed at rest (revocable, unlike a bare JWT refresh token would be), and real
server-side password strength enforcement (findme_app's `passwordStrength.ts` was
UX-only before -- see its own "Known gaps" -- because there was no equivalent
enforcement point on this side either until now).

**Supabase Auth's phone OTP -> `app/services/phone_verification.py` +
`app/services/sms.py`.** This service now owns OTP generation, hashing, expiry, and
attempt-limiting directly (`phone_otps` table) instead of delegating to a managed
provider. Defaults to a `console` SMS provider that logs the code instead of sending
one -- **switch `SMS_PROVIDER=twilio` and fill in the three `TWILIO_*` vars before this
is usable in production.**

**Stripe was NOT carried forward.** It was already unused in the app you have --
M-Pesa STK Push (`app/services/mpesa.py`, `app/routers/billing.py`) is the real payment
path, ported in full including the callback's referral-commission logic. If you need
Stripe for a non-Kenyan market later, it's a clean addition on top of this structure
(a `stripe.py` service + two routes mirroring `mpesa.py`/`billing.py`), not a
prerequisite for anything else here.

**Database Webhooks + Edge Functions -> synchronous in-process calls.**
`consent-notify` and `geofence-evaluate` used to be separate Deno functions triggered
by a webhook after a write committed. Now `app/services/push.py` and
`app/services/geofence_eval.py` are called directly from the same request that
triggers them (`POST /consents`, `PATCH /consents/{id}`, `POST /devices/{id}/pings`).
Net effect is identical (a push notification / geofence event gets created), but a
slow Expo push call now adds latency to the triggering request itself rather than
happening out-of-band. If that becomes a problem at scale, moving `push.py` calls onto
a background task queue (Celery, arq, or even FastAPI's `BackgroundTasks`) is a
contained change -- the call sites are already isolated.

**`ingest-news`/`ingest-conflict-events` -> cron-secret-gated HTTP endpoints,
not scheduled themselves.** Supabase could wire these to `pg_cron`. This service has
no built-in scheduler -- point any external cron (a real cron job, GitHub Actions on a
schedule, Render/Fly.io's cron jobs) at `POST /ingest/news` and
`POST /ingest/conflict-events` with the `x-cron-secret` header set to
`CRON_SHARED_SECRET`.

**`find_profile_for_invite`/`resolve_login_email` -> `GET /auth/lookup` /
`POST /auth/login`.** Same narrow-lookup and anti-enumeration intent, same unclosed
side channel: `authenticate()`'s docstring notes explicitly that this narrows but does
not close user enumeration via response timing/behavior. Rate limiting this endpoint
(and `/auth/signup`) is the same "known gap, needs to happen before this handles real
traffic" item the Supabase version flagged and never closed either.

## Known gaps (carried forward or new)

- **No rate limiting anywhere.** Not on `/auth/login`, `/auth/signup`,
  `/auth/phone/send-otp`, or `/billing/mpesa/stk-push`. Add `slowapi` or a reverse-proxy
  (nginx/Caddy) rate limit before any of this is internet-facing.
- **`/billing/mpesa/callback`'s only real protection is URL secrecy** -- ported
  unchanged from the Supabase version's own noted gap. A production deployment
  fronting real money should add a shared-secret query parameter that Safaricom echoes
  back, verified before processing.
- **ACLED conflict-event ingestion is still a stub** (`app/services/conflict_ingest.py`)
  -- same as the original; `fetchEvents()`/`_fetch_events()` was never wired to a real
  feed, ACLED or otherwise. `ACLED_API_KEY` being set doesn't change this until that
  TODO is closed.
- **No background job queue.** Push notifications and geofence evaluation run
  synchronously inside the request that triggers them (see above). Fine at this scale;
  revisit if `POST /devices/{id}/pings` latency becomes noticeable under load.
- **Intel-photo uploads are stored, not analyzed.** `/uploads/intel-photo` is the
  storage half of the PRD's "track a device via an uploaded photo" feature -- there is
  no EXIF extraction, reverse image search, or any OSINT processing here. That's a
  distinct, substantial piece of work this rewrite didn't attempt.
- **`findme_app` still talks to Supabase directly.** Every file in `findme_app/lib/`
  (`supabase.ts`, `auth.tsx`, `consent.ts`, `map.ts`, `billing.ts`, etc.) calls
  `supabase-js` / Supabase RPCs, none of which exist anymore once this backend replaces
  `findme_backend/`. **The mobile app needs a follow-up pass**: a new `lib/api.ts` HTTP
  client wrapping this service's REST endpoints + JWT storage (replacing
  `supabase.auth`'s session handling, likely still via `AsyncStorage`), and each
  `lib/*.ts` file rewritten to call it instead of `supabase.from(...)`/`.rpc(...)`. The
  endpoint map above should make that a fairly mechanical one-to-one swap per screen.

## Verification

This was built in a sandboxed environment with no Docker and no root access, so a real
PostgreSQL+PostGIS instance was never reachable here. What WAS verified:

- **Every `.py` file compiles** (`python -m py_compile`) and **the full FastAPI app
  imports and registers all 34 routes** (`from app.main import app` + inspecting
  `app.openapi()`).
- **27 pure unit tests pass** (`pytest tests/test_security.py tests/test_phone.py
  tests/test_geo.py tests/test_authz_pure.py`) -- password hashing/JWT roundtrips,
  phone/MSISDN normalization, PostGIS coarsening math, and the plan-limit/effective-
  plan-tier logic that doesn't require a database.
- **The Alembic migration generates valid SQL end to end**
  (`alembic upgrade head --sql`), including the PostGIS extension, all 16 tables, every
  check constraint, the partial unique index on `consents`, and both GIST indexes.
- **`pyflakes` reports zero undefined-name/logic errors** across `app/` and `alembic/`.

**What was NOT run here and needs verification on a machine with Docker**: the 7
integration tests in `tests/test_integration_flows.py` (signup/login, the free-plan
device limit, consent request/approve/audit-trail, precise-scope plan gating, duplicate
consent-request conflict handling, and full geofence enter/exit alert generation against
real PostGIS `ST_DWithin`). They're written and will collect/skip cleanly without a
database; run them for real with:

```
docker compose up -d db
FINDME_TEST_DATABASE_URL=postgresql+asyncpg://findme:findme@localhost:5432/findme \
    pytest tests/test_integration_flows.py -v
```

Also unverified here for the same reason: an actual `docker compose up` (image build +
container networking), a real MinIO upload round trip, and a real Daraja sandbox STK
Push call (needs real `MPESA_*` credentials). Run all of these before considering this
production-ready.
